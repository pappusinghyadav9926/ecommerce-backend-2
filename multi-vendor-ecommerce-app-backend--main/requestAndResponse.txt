1. ARCHITECTURAL OVERVIEW & KEY HIBERNATE FEATURES SHOWCASED
----------------------------------------------------------------------------------------------------

1. Bidirectional Mappings:
   - User (Parent) <---> @OneToOne(mappedBy = "user", cascade = CascadeType.ALL) <---> CustomerProfile (Child)
   - Category (Parent) <---> @OneToMany(mappedBy = "category", cascade = CascadeType.ALL) <---> Product (Child)
   - Vendor (Parent) <---> @OneToMany(mappedBy = "vendor", cascade = CascadeType.ALL) <---> Product (Child)
   - Product (Owning) <---> @ManyToMany(via @JoinTable(name = "cart_product")) <---> Cart (Non-Owning)
   - Order (Parent) <---> @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true) <---> OrderItem (Child)

2. Soft Deletes (@SQLDelete & @SQLRestriction):
   - Products are annotated with:
     @SQLDelete(sql = "UPDATE product SET is_deleted = true WHERE id = ?")
     @SQLRestriction("is_deleted = false")
   - When product.deleteById(id) is invoked, Hibernate intercepts the operation and issues an UPDATE SQL query instead of a physical SQL DELETE. Active JPQL and Spring Data repository queries automatically filter out soft-deleted items while preserving historical OrderItem records intact.

3. Batch Processing (Bulk Seller Upload Optimization):
   - Configured JDBC Batching in application.properties:
     hibernate.jdbc.batch_size=50
     hibernate.order_inserts=true
     hibernate.order_updates=true
   - ProductService.saveBatchProducts iterates over product requests, invokes entityManager.persist(product), and executes entityManager.flush() and entityManager.clear() every 50 records.
   - Prevents OutOfMemory exceptions and groups single SQL INSERT statements into batch SQL executions sent over JDBC.

4. Orphan Removal (Automatic Cleanup):
   - Configured @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) on Order.orderItems.
   - When an OrderItem is removed from the order.getOrderItems() collection, Hibernate dirty-checking detects the dereferenced entity and issues an automatic SQL DELETE statement:
     DELETE FROM order_item WHERE id = ?

5. N+1 Problem Solution in Order Retrieval (Interview Challenge):
   - Challenge: Default lazy loading inside loops when fetching a customer's order history generated 1 SQL query for Orders + N queries for OrderItems + M queries for Products (1 + N + M total queries).
   - Solution: Replaced lazy loop fetching with JPQL JOIN FETCH in OrderRepository:
     "SELECT DISTINCT o FROM Order o JOIN FETCH o.orderItems oi JOIN FETCH oi.product WHERE o.customer.id = :customerId"
   - Result: Consolidates query execution into 1 single optimized SQL JOIN statement.

6. Database Indexing & Caching:
   - Indexing: @Table(name = "product", indexes = {@Index(name = "idx_product_name", columnList = "name"), @Index(name = "idx_product_category", columnList = "category_id"), @Index(name = "idx_product_vendor", columnList = "vendor_id"), @Index(name = "idx_product_price", columnList = "price")}).
   - Indexing: @Table(name = "orders", indexes = {@Index(name = "idx_order_customer", columnList = "customer_id"), @Index(name = "idx_order_status", columnList = "status")}).
   - Spring Cache: @EnableCaching with @Cacheable(value = "products", key = "#id") and @CacheEvict(value = "products", key = "#id").

3. STEP-BY-STEP CODE EXECUTION FLOW
----------------------------------------------------------------------------------------------------

SCENARIO 1: User Registration & Customer Profile Creation (@OneToOne)
  1. Client sends POST to /api/users with UserDTO.Request payload.
  2. UserController intercepts request and invokes UserService.createUser(request).
  3. UserService constructs User and CustomerProfile entities, linking them via user.setCustomerProfile(profile).
  4. UserRepository.save(user) is invoked.
  5. JPA/Hibernate Persistence Context persists both User and CustomerProfile in a single transaction via CascadeType.ALL.
  6. MySQL executes 2 SQL INSERT queries:
     - INSERT INTO users (username, email, password, role, created_at) VALUES (?, ?, ?, ?, ?);
     - INSERT INTO customer_profile (first_name, last_name, phone, shipping_address, city, state, zip_code, country, user_id) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?);

SCENARIO 2: Bulk Product Upload (Batch Processing Optimization)
  1. Seller submits POST to /api/products/batch with a list of product requests.
  2. ProductController calls ProductService.saveBatchProducts(requests).
  3. ProductService loops over the requests and persists products using entityManager.persist(product).
  4. Every 50 iterations (matching hibernate.jdbc.batch_size=50), ProductService calls:
     - entityManager.flush() -> Flushes pending inserts to database batch queue.
     - entityManager.clear() -> Clears persistence context to free heap memory.
  5. MySQL JDBC Driver receives batched INSERT commands:
     - INSERT INTO product (name, sku, description, price, stock_quantity, category_id, vendor_id, is_deleted) VALUES (?, ?, ?, ?, ?, ?, ?, ?); [Batch of 50]

SCENARIO 3: Soft Product Deletion (@SQLDelete)
  1. Client sends DELETE request to /api/products/{id}.
  2. ProductController delegates to ProductService.deleteProduct(id).
  3. ProductService calls ProductRepository.deleteById(id).
  4. Hibernate intercepts deleteById and inspects @SQLDelete annotation on Product entity.
  5. Instead of issuing "DELETE FROM product WHERE id = ?", Hibernate executes:
     - UPDATE product SET is_deleted = true WHERE id = ?;
  6. Historical order items referencing this product remain safe. Subsequent product searches automatically append "WHERE is_deleted = false" due to @SQLRestriction.

SCENARIO 4: Placing an Order & Orphan Removal
  1. Client sends POST to /api/orders.
  2. OrderController calls OrderService.createOrder(request).
  3. OrderService fetches customer and products, calculates subtotals, constructs OrderItem entities, and attaches them to Order via order.addOrderItem(item).
  4. OrderRepository.save(order) cascades persist to OrderItems (CascadeType.ALL).
  5. When client deletes an item via DELETE /api/orders/{orderId}/items/{orderItemId}, OrderService invokes order.removeOrderItem(item).
  6. Hibernate dirty checker notices the OrderItem removed from order.getOrderItems() collection and issues:
     - DELETE FROM order_item WHERE id = ?; (Triggered by orphanRemoval = true).

SCENARIO 5: N+1 Solution in Order History Retrieval (JPQL JOIN FETCH)
  1. Client calls GET /api/orders/customer/{customerId}.
  2. OrderController delegates to OrderService.getOrdersByCustomerId(customerId).
  3. OrderService calls OrderRepository.findByCustomerIdWithItemsAndProducts(customerId).
  4. OrderRepository executes JPQL query:
     "SELECT DISTINCT o FROM Order o JOIN FETCH o.orderItems oi JOIN FETCH oi.product WHERE o.customer.id = :customerId"
  5. Hibernate translates JPQL into 1 single SQL statement executed on MySQL:
     SELECT DISTINCT o.id, o.order_number, o.total_amount, o.status, o.order_date,
            oi.id, oi.quantity, oi.unit_price, oi.subtotal,
            p.id, p.name, p.sku, p.price
     FROM orders o
     INNER JOIN order_item oi ON o.id = oi.order_id
     INNER JOIN product p ON oi.product_id = p.id
     WHERE o.customer_id = ?;
  6. Eliminates N+1 database round-trips down to 1 single JOIN fetch query.
